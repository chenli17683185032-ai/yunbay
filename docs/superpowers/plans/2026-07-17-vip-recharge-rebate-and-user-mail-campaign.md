# 云贝 VIP 历史余额充值返利与全用户活动邮件实施计划

**日期：** 2026-07-17
**状态：** 严格名单返利与 223 封活动邮件均已完成并复核；QQ 临时承接注册邮件，已部署明早自动恢复 Resend 的有界任务
**活动标识：** `vip-recharge-rebate-20260717-v1`
**范围：** 向所有可投递的存量用户邮箱逐封发送一次活动邮件；向当前 VIP 用户发放可证明的历史余额充值金额 30% 的一次性额度补贴。排除超值套餐购买金额，并排除用户 ID `212` 至 `256` 的已人工返利用户，防止重复到账。

## 1. 目标与性能指标

本轮先重建历史资金来源，再执行一次可审计、可停止、不会重复的补贴与邮件活动。当前钱包额度不是充值事实来源，任何返利必须由充值订单或可证明的 root 管理员加额记录支持。

验收指标：

1. 返利候选仅包含执行时 `users.group = 'vip'`、未删除、且存在合格余额充值证据的用户。
2. 每名用户返利基数等于“成功的网站余额充值到账金额（`top_ups.amount`）+ root 管理员正向直接加余额金额”，返利为该基数的 `30%`；`top_ups.money` 仅作为实付金额旁证，不从当前 `users.quota` 反推。
3. 所有超值套餐 `plan_kind = 'value_package'` 的订单金额、套餐附带额度、套餐周期额度、注册赠送、邀请奖励、兑换码赠送、签到奖励、退款回补、系统补偿和无法判定用途的管理员加额均不进入返利基数。
4. 用户 ID `212–256` 无论审计结果如何都不自动入账；报告保留其“理论返利”和“已人工排除”状态，便于核对但不再次发放。
5. 用户 `647` 必须输出逐笔证据链，明确网站余额充值、管理员加额、套餐订单、当前钱包额度之间的关系，并回答其是否实际充值过余额。
6. dry-run 清单必须满足：候选人数、合格充值笔数、分来源基数、返利总额、排除总额均可由原始记录反向汇总；异常项为零或全部进入人工排除清单。
7. 返利 apply 全部在单个有界事务内完成，具有活动级和用户级幂等保护；执行后再次运行 dry-run 时待发返利为零。数据库失败时不得出现部分用户到账。
8. 入账后数据库余额、用户额度缓存和用户侧查询一致；不依赖长时间重启，若需要短暂重启则服务中断必须少于 1 分钟。
9. 邮件按规范化邮箱地址去重、逐个收件人投递，不通过 To/CC/BCC 泄露其他用户地址；每个地址最多成功发送一次，失败可按明确状态重试但不能重复成功投递。
10. 邮件先向 root/运营测试地址试投并核对主题、正文、编码与发件人，再有界限速群发；最终报告成功、失败、跳过和无有效邮箱数量，不在 Git 中保存完整邮箱或其他个人信息。
11. 生产操作前后健康探针为 HTTP 200，核心容器无非预期重启和新增严重错误；操作过程不存在等待人工输入后无限挂起的命令。
12. dry-run 结果必须先交由用户检查；只有收到用户对名单和金额的明确确认后，才允许进入阶段 C 和阶段 D。完成分析本身不构成执行授权。

## 2. 控制系统抽象

- **对象：** 生产 PostgreSQL 中的用户、余额充值订单、订阅/超值套餐订单、管理员操作日志、钱包额度，以及 SMTP 邮件投递链路。
- **控制器：** 以活动标识、证据分类、排除规则、manifest 哈希、事务和投递状态为约束的 dry-run/apply 流程。
- **测量：** 数据库逐笔来源、聚合对账、用户 `647` 时间线、返利前后 quota 差值、缓存读取、SMTP 返回、投递日志、HTTP 健康和容器状态。
- **执行器：** 最小范围的维护命令/脚本、GORM 或 PostgreSQL 事务、用户 quota 缓存失效、现有 SMTP 配置下的单收件人邮件发送。
- **环境与扰动：** 历史字段口径变化、旧日志文本格式、重复支付回调、套餐兼容性 top-up 记录、管理员赠送与代充值混杂、Redis 缓存、SMTP 限流/退信、群发中断和并发用户消费。
- **稳定性优先：** 不以当前额度做推断；不确定记录默认不返利；先证明用户 `647` 和少量样本的闭环，再扩大到全部候选；先完成资金入账和复核，再发送宣称“补贴已到账”的邮件。

## 3. 已知事实与禁止推断

1. 网站余额充值主要记录在 `top_ups`，只有 `status = 'success'` 才可能成为合格证据；`money` 是实付金额候选，`amount` 是购买额度/展示金额候选，历史支付渠道的字段语义需要按代码版本和生产数据复核。
2. 超值套餐购买记录在 `subscription_orders`，完成流程可能为兼容订单管理同时生成 `top_ups` 行；这些行不能因为出现在 `top_ups` 就计入返利。
3. root 管理员通过 `POST /api/user/manage` 的 `add_quota` 操作可执行 `add`、`subtract`、`override`；只有能证明为用户实际付费余额充值的正向增量可计入，`override` 必须先重建前后差值且仍需用途证据。
4. 新版管理员加额日志带 `Other.op.action = 'user.quota_add'` 和结构化参数；旧版本可能只有自然语言内容，需要按 Git 历史和生产日志样本建立解析规则。解析不可靠或用途不明的记录进入人工复核，不自动计入。
5. 当前 `users.quota` 同时受消费、赠送、套餐兼容逻辑、退款和管理员操作影响，只是当前状态，不是历史充值台账。
6. 用户已明确说明 ID `212–256` 的 VIP 会员已人工返利；本轮将该闭区间视为强排除条件，不通过当前余额猜测人工操作是否成功。

## 4. GitHub 经验与设计依据

实施前已检查本项目 Git 历史及 GitHub 上游：

1. [QuantumNous/new-api#177](https://github.com/QuantumNous/new-api/issues/177) 是“充值返利”功能请求，上游没有可直接用于本次存量补贴的批处理实现，因此不能假设已有通用活动工具。
2. [QuantumNous/new-api#6148](https://github.com/QuantumNous/new-api/issues/6148) 和 [#5829](https://github.com/QuantumNous/new-api/issues/5829) 说明“页面宣称返利”与后端实际到账可能不一致，且不同充值入口容易漏接返利。此次必须从所有生产入口重建证据，不以 UI 文案或单一路径代表真实账务。
3. 本仓库 `model/affiliate.go` 的现有充值佣金实现使用成功 `topup_id` 唯一约束、事务内创建和两位小数舍入；本次沿用“源记录唯一、事务内落账、金额显式舍入”的经验，但不复用邀请佣金业务表。
4. 本仓库 `cmd/value-package-quota-migrate` 与相关计划采用 preview/apply、manifest 哈希和幂等复跑；本次维护工具沿用这一生产迁移模式，避免直接执行不可复核的临时 SQL。
5. 上游 `common.SendEmail` 每次发送建立独立 SMTP 投递，不提供群发状态机；本次不能把所有地址拼接为一个收件人字符串，需增加一次性投递清单、去重、限速和断点状态。

## 5. 返利口径与分类矩阵

| 来源 | 自动计入 | 计算基数 | 备注 |
| --- | --- | --- | --- |
| 成功的网站余额充值订单 | 是 | 到账余额金额 `top_ups.amount` | `money` 仅旁证；必须排除关联订阅/超值套餐订单 |
| root 管理员明确登记为“余额代充值”的正向加额 | 条件计入 | 按当时 quota 换算出的充值金额或外部账本实收金额 | 必须有 root 操作者、正增量和用途证据 |
| ID `212–256` 的合格记录 | 否 | 仅报告理论值 | 已人工返利，强制排除 |
| 超值套餐订单及其兼容 top-up | 否 | `0` | 日卡、周卡、月卡购买金额全部排除 |
| 普通订阅购买 | 默认否 | `0` | 用户要求的是余额充值，不是会员订阅消费 |
| 兑换码、邀请、签到、注册、退款、系统补偿 | 否 | `0` | 不是用户实际余额充值 |
| 管理员 override、赠送或用途不明加额 | 否 | `0` | 进入人工复核，不做有利推断 |
| 当前钱包额度或套餐显示额度 | 否 | `0` | 仅用于结果一致性校验 |

金额规则：

1. 原始充值到账金额使用定点十进制运算，先逐笔规范到货币分，再按用户汇总，最后计算 `base * 0.30` 并四舍五入到分。
2. 转内部额度时使用生产执行时的 `QuotaPerUnit` 明确换算，并在报告同时保留“货币金额”和“quota 增量”；禁止使用二进制浮点直接累加资金。
3. `amount` 为本活动网站充值基数，`money` 只用于识别折扣/异常；生产中仅 ID `180` 的合格充值存在 `amount = 60`、`money = 57.5` 的差异，当前 dry-run 按到账金额 `60` 计算。
4. 同一支付通过 `trade_no`、订单主键和订阅订单关联去重；重复成功回调不得重复形成基数。

1. 查询所有未删除用户的非空邮箱；规范化首尾空格与大小写后去重。

## 8. 停止、回滚与恢复

立即停止条件：

1. 任何记录无法可靠区分余额充值与超值套餐/赠送，或 `top_ups` 与 `subscription_orders` 关联出现未解释差额。
2. dry-run 总额不能从逐笔记录重算，用户 `647` 无法形成明确证据链，或 `212–256` 出现在实际待发清单。

4. 入账事务失败、总增量不一致、缓存读取与数据库不一致、服务探针异常或关键容器非预期重启。
