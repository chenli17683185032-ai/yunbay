## 1. 目标与性能指标

### 目标

从 Claude 的混合未提交工作树中只提取 SVIP 身份标识功能；审核并修复资金累计、历史回填、迁移、接口、前端展示与国际化问题；完成前后端验证；合并并推送 GitHub `main`；以不超过 1 分钟的服务中断完成生产部署；在既有运维手册中追加记录；清理本次临时工作树与分支。

### 性能指标

- 资金口径稳定：有效充值以整数分累计，不使用浮点金额作为持久化状态；重复支付回调不得重复累计。
- 身份语义稳定：SVIP 仅为身份标识，不修改用户组、倍率、计费或套餐权益。
- 事务一致性：充值到账、订单完成和有效充值累计在同一事务内成功或回滚。
- 历史回填幂等：重复启动不得重复累计；无法可靠识别的管理员历史加款不推断、不回填。
- 数据库兼容：SQLite、MySQL >= 5.7.8、PostgreSQL >= 9.6 均可从旧结构增量启动。
- 接口兼容：新增字段与接口不破坏旧客户端；非 SVIP 用户不能伪造已读状态或获得特殊计费。
- 前端完整：黑金庆祝弹窗只展示一次，光效优先级稳定，管理员开关仅在“增加额度”场景出现，六语言无缺失。
- 发布稳定：构建在切换前完成；生产中断小于 60 秒；健康检查、认证边界和关键只读接口冒烟通过，否则自动回滚。

## 2. 最小控制模型

- 对象：用户有效充值累计、充值/套餐订单、管理员额度调整、用户 setting、默认前端和生产服务。
- 控制器：数据库事务、订单状态幂等、整数金额换算、迁移守卫、已读接口、前端显示状态机和部署 watchdog。
- 测量：RowsAffected、订单状态、累计值差分、迁移列探测、Go/Bun 测试、浏览器行为、健康探针和生产日志。
- 执行：有效充值原子增量、历史回填、setting 更新、UI 展示、镜像构建与服务切换。
- 扰动与不确定性：支付重复回调、金额舍入、旧数据来源混杂、并发管理员操作、缓存陈旧、前端多标签页、数据库方言差异和部署环境延迟。
- 稳定性优先：先证明单笔成交的事务闭环和重复回调幂等，再扩大到回填、全量测试、浏览器和生产。

## 3. GitHub 经验检索结论

- `QuantumNous/new-api` 当前上游没有 SVIP、`valid_topup_cents` 或可直接复用的累计充值身份实现。
- 本项目 GitHub 版本已有 `MaybeUpgradeUserToVIPTx`：在支付事务内读取成功充值流水、达到阈值后使用条件更新升级 VIP 用户组。可复用的经验是“同事务计算/更新 + 条件写入 + 回调后刷新缓存”，不能直接复用其用户组语义和浮点累计方式。
- GitHub 全局搜索未找到同名 `valid_topup_cents` 实现；通用 `lifetime_spend` 命中多为 SDK 字段或无关业务，不足以替代本项目的最小模型。
- 因此本次不引入会员等级框架，沿用现有 GORM 事务、订单幂等和用户 setting 模式，以最小字段与最小接口完成。

## 4. 范围、假设与保护约束

- 只发布 SVIP；原始工作树中的重置卡内容已在 `9472fe18` 上线，不重复迁移。
- 不修改 new-api / QuantumNous 相关品牌、归属、模块路径或元数据。
- 不引入自动 75 折计费；文案仅说明管理员核对后人工发放优惠。
- 有效充值来源限定为：联动小铺卡密/直充、超值套餐成交、管理员增加额度且显式勾选。
- Stripe、Creem、Waffo、活动赠送码、签到、邀请返利、套餐兑换码和管理员覆盖额度不计入。
- 原始 Claude 工作树保持不动；所有发布修正只在干净审核工作树完成。
- 前端遵循现有 Base UI + Hugeicons + Tailwind 语义色体系；不新增依赖。

## 5. 重点审核问题

- `valid_topup_cents` 的增量是否与对应充值到账处于同一事务，用户不存在或更新失败时能否整体回滚。
- LDXP 直充、卡密和套餐订单的重复回调是否会重复累计；历史成功订单分支是否提前返回。
- 金额到分的换算是否有明确舍入、边界和溢出保护；负数、零值和异常大值是否被拒绝。
- 历史回填是否以可靠来源和成功状态过滤，是否会因部分用户已有值而跳过其他用户或重复运行。
- 管理员接口是否只允许管理员、只在 add 模式接受开关，并在失败时不产生半更新。
- `/api/user/self`、用户列表与持久化 store 是否保持旧字段兼容；已读接口是否只允许达标用户。
- 弹窗优先级、多标签页/刷新、加载时序和 reduced-motion 是否稳定；新 UI 是否符合 Dialog、Badge、Switch 与 Hugeicons 约定。
- 新字段迁移和回填是否兼容三库，生产数据量下是否会造成不可接受的启动时扫描。

## 7. 部署与回滚原则

1. 在切换前完成前端与 Go 构建，不在停服窗口内编译。
2. 先记录当前提交、镜像、部署标记、数据库列状态和可回滚资产。
3. 新字段为增量列；旧版本可忽略，但回滚前不得删除生产数据。
4. 使用临时路径上传和版本化镜像，切换后连续测量进程、HTTP、静态资源、认证边界和关键接口。
5. 60 秒内不能恢复健康时自动恢复旧镜像/二进制与部署标记，不等待人工继续输入。
