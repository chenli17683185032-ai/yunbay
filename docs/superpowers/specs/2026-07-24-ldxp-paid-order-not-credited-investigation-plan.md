## 2. 目标、性能指标与闭环

### 2.1 目标

建立一条可重复核验的证据链：

```text
LDXP/支付宝已支付
  -> ldxp_topup_sessions 捕获支付结果
  -> 验证/兑换事务成功
  -> top_ups 成功账本唯一落库
  -> users.quota 增加
  -> 客户可见余额更新
```

最终必须把故障定位到该链路中的一个明确断点，而不是仅凭页面状态推断。

### 2.2 验收指标

- 用订单号精确找到唯一 LDXP 会话；若找不到，解释订单与云贝会话为何失联。
- 对比会话的 `status`、`worker_detected_time`、`verified_time`、`redeemed_time`、`topup_id`、`redemption_id` 和错误码。
- 核对关联 `top_ups`、用户额度及必要的兑换/套餐账本，排除“实际已入账但前端未刷新”。
- 将 11:03:46 至 11:04:16 前后日志与数据库状态关联，确认 worker 是否保持同一活收银台、是否检测成功页、回调是否被后端接受。
- 所有查询只读、命令有界，不打印密钥、令牌、cookie、完整二维码或用户隐私。
- 不允许因查询或日志等待而无限阻塞；任何实时命令都设置固定时间窗口。

## 4. 控制系统抽象

- 对象：LDXP 商品页、LinkPay 跳转、支付宝收银台及支付状态演化。
- 控制器：LDXP browser worker 和 new-api 会话/验证/兑换服务。
- 测量：收银台成功页面、worker result callback、可选邮件审计信号。
- 执行器：创建成功 `top_ups`、增加用户 quota 或激活对应超值套餐。
- 反馈：会话状态时间戳、账本外键、额度差异和前端查询结果。
- 主要扰动：ESA/WAF、代理/订阅失效、浏览器页面关闭、worker 重启、超时、并发槽位饱和、回调网络失败、订单金额含手续费、邮件延迟。
- 稳定性约束：一次支付最多入账一次；不因缺少邮件阻塞可信成功页；未知状态不可自动补款；查询与恢复均须有界。

## 5. 最小充分诊断模型

按状态逐层缩小范围：

1. `created/worker_claimed`：订单未正确关联或 worker 未完成二维码阶段。
2. `qr_ready` 且 `worker_detected_time=0`：支付宝已付，但 worker 没观察到成功页；重点查页面生命周期、worker 重启/异常、active-check 和代理。
3. `worker_paid`：worker 已检测付款，但后端验证或后续兑换未完成；查 error code、金额/订单校验和恢复任务。
4. `verified`：卡密或订单已验证，执行入账事务失败或等待恢复。
5. `success` 且 `topup_id>0`：后端宣称成功；查 `top_ups`、用户 quota、套餐订阅及前端缓存，防止误补。
6. 无会话但第三方有订单：检查创建过程关联丢失、旧/直购入口或用户是否在另一个会话中支付。

### 7.2 为什么没有到账

- 会话最终是 `canceled`，且 `worker_detected_time=0`、`verified_time=0`、`redeemed_time=0`、`topup_id=0`、`redemption_id=0`。
- `top_ups` 中不存在 `ldxp:LD260724SG04DI`，用户在该时间段也没有对应兑换记录，因此不是前端缓存或余额显示问题，后端确实没有为本单入账。
- 当前 `LDXP_RELEASE_SLOT_AFTER_QR=false`，正常情况下 worker 会保持原支付宝页面；本次是用户侧已认证取消请求使 active-check 主动终止页面，并非槽位提前释放配置回归。
- `LDXP_REQUIRE_MAIL_MATCH=false`，所以邮件不是正常成功的前置条件；但当前 worker 的 IMAP 配置不完整，mail poller 已禁用，因此本单取消后也没有第二条邮件审计/恢复信号。
- 同一用户后续 10 刀订单 `LD2607241QLL75` 在 11:11:41 正常上报 `result posted` 并创建成功 `top_ups.id=70`。这证明 worker、代理和后端入账事务当时可用，也证明后续 10 刀到账不是本单 100 刀的补偿。

### 7.3 产品层缺口

- `qr_ready` 状态仍显示一个直接调用后端取消接口的“取消”按钮，没有二次确认。
- 后端的 `canceled` 只终止云贝观测，并没有能力同步撤销已经创建的 LDXP/支付宝订单。
- 因此用户扫码后若把“取消”理解成关闭窗口，外部付款仍可完成，但云贝已经停止观察，形成可重复的已付未到账路径。

### 7.4 恢复与防复发建议

- 本单：先以渠道流水号和订单后台再次确认不可退款/未退款，再通过现有幂等充值管理路径为用户补 100 刀；操作前再次查询 `top_ups.trade_no`，防止并发补偿或迟到恢复造成重复入账。本轮没有执行。
- UI：把“关闭窗口”和“放弃未付款订单”拆开；`qr_ready` 后关闭 UI 不应取消后端会话。真正放弃必须明确提示“已扫码或已付款请勿取消”并二次确认。
- 后端：外部订单已经创建后，不应把本地 cancel 直接等价为关闭观测；至少保留一个有界宽限期，或先确认第三方订单确实未支付。
- 恢复通道：恢复可靠的 IMAP 审计，或增加可幂等的订单对账/人工恢复入口，使 `canceled + 第三方已支付` 可以按订单号安全收敛，而不是依赖仍存活的单个浏览器页面。

## 8. 查询与安全边界

- 生产查询优先通过容器内 `psql` 执行明确 `SELECT`，不执行 `UPDATE/INSERT/DELETE`。
- 查询结果只保留诊断所需字段；用户名、邮箱、令牌等信息不在对话中披露。
- 日志用精确订单号、会话 ID 和固定时间窗过滤，避免导出整库或全部日志。
- 不读取或输出 `prod.env` 全文；只对所需布尔/数值配置生成脱敏摘要。
- 若数据库表结构或列名与计划不同，先只读查看 schema，再调整查询。
- 若确认订单缺失入账，任何人工修复必须复用现有幂等事务/管理入口，并在操作前重新确认没有并发恢复任务。
