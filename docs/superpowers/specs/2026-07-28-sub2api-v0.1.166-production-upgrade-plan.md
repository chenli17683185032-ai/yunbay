## 2. Goal And Performance Metrics

The goal is not merely to start a newer container. The closed-loop outcome is:

1. Production runs the exact official `0.1.166` Linux amd64 image.
2. All pre-existing configuration remains effective and unchanged.
3. Existing PostgreSQL and Redis data remain in place.
4. Only `yunbay-sub2api` is recreated; Caddy, new-api, PostgreSQL, Redis, CLI Proxy, LDXP, Grok, and iCloud services keep their container identities and restart counters.
5. The public and container-local health endpoints recover within 60 seconds.
6. Migration and startup logs contain no fatal, panic, checksum mismatch, or failed migration event.
7. A bounded watchdog automatically restores the old image reference if the new instance does not become stably healthy; it must never wait indefinitely for operator input.

## 3. Control-System Model

Following the project control doctrine, this deployment is treated as a dynamic process rather than a static file replacement.

| Element | Concrete object |
| --- | --- |
| Controlled object | The production Sub2API process, its PostgreSQL schema, Redis cache use, and public route |
| Controller | The version-pinned rollout script, deployment lock, health loop, and automatic rollback branch |
| Actuator | `docker compose up -d --no-deps --force-recreate sub2api` |
| Measurements | Image labels/digest, Docker health, local/public HTTP probes, migration state, logs, config/environment fingerprints, sibling container identities |
| Environment | Shared Caddy network, shared PostgreSQL 15, shared Redis 7, natural API traffic, upstream provider latency |
| Disturbances | Image pull failure, migration delay, checksum mismatch, port/network readiness delay, transient 502, upstream network noise, SSH disconnect |
| Saturation and delay | Container startup and migration time; healthcheck start period; 60-second user tolerance |

The stable loop is proved first on an isolated database and Redis copy, then applied once to production. Speed is secondary to bounded recovery and preservation of state.

- Official installation command names Docker Hub image `weishaw/sub2api:0.1.166`
- Docker Hub resolves the Linux amd64 platform image to `sha256:27fe46f83e27d6a63857b4d6c59297eff619fdfb50d94450b1b2d02f546d4148`
- Releases `0.1.156` through `0.1.166` contain no explicit breaking-upgrade instruction; the documented Docker upgrade pattern remains image replacement followed by normal startup
- Relevant fixes include OpenAI failover and streaming repairs, WebSocket lifecycle and multi-turn billing corrections, request-path performance work, graceful shutdown billing preservation, PostgreSQL 15 Ollama refresh repair, partial-setting update preservation, and panel API rate limiting
- Source comparison shows additive migrations from the current production baseline through `190_add_users_email_alias_dedup_index_notx.sql`
- The migration runner serializes startup migrations with a PostgreSQL advisory lock, runs ordinary migrations transactionally, validates checksums, and reserves non-transactional execution for concurrent indexes

Risk conclusion: the database changes are meaningful enough to require an isolated restored-database rehearsal, but the official migration design supports an in-place upgrade and old binaries ignore later migration records. Automatic rollback therefore restores the old binary and Compose image only; it must not destructively reverse the database or restore older settings.

## 6. Invariants: Settings Must Not Be Rolled Back

The following are immutable inputs for this rollout:

- `/opt/new-api/sub2api/data/config.yaml`
- All existing Compose environment values, including credentials and feature flags
- Database and Redis connection targets
- Existing settings rows and their values
- Accounts, groups, priorities, schedulability, proxies, keys, billing rules, model mappings, OAuth credentials, custom routes, monitoring rules, and panel settings
- Caddy configuration and routing
- PostgreSQL and Redis containers and volumes
- All non-Sub2API services

No admin API mutation, settings import, database restore, configuration regeneration, or volume replacement is authorized. `AUTO_SETUP=true` may run the upstream idempotent startup path, but the rollout will compare existing settings before and after.

The isolated rehearsal exposed one intentional upstream compatibility migration in `LoadForwardedClientIPSettings`: when `server.trusted_proxies` was never configured, the legacy persisted key `api_key_acl_trust_forwarded_ip=false` is changed to `true`, while `forwarded_client_ip_headers=[]` and `forwarded_client_ip_mode_v2_migrated=true` are added. The new server still disables trusted proxies and uses direct peer addresses, so the effective IP trust boundary remains unchanged. This exact `false -> true` compatibility transition is allowed; any other pre-existing key/value change is a stop condition.

## 8. Rollback Contract

Automatic rollback trigger: the new container does not become stably healthy within 60 seconds, exits after being observed running, or fails the local source probe.

Rollback action:

1. Hold the same dedicated deployment lock.
2. Restore only the backed-up Compose file or old image line.
3. Recreate only `yunbay-sub2api`.
4. Verify old local and public health.
5. Leave PostgreSQL migrations and all settings in place because the upstream changes are additive and the old migration runner ignores later migration records.
6. Keep the database dump for disaster recovery, but do not apply it during normal rollback.

Manual database restore is a last-resort destructive recovery action and is outside the automatic path. It requires separate evidence that the database itself was corrupted and explicit operator approval.
