### 目标

### 性能指标

- 资金与权益稳定性：同一兑换码并发请求至多成功一次；任一步失败时兑换码状态、重置卡余额和台账全部回滚。

## 3. GitHub 经验检索结论

- `QuantumNous/new-api` 当前 `model/redemption.go` 使用 `DB.Transaction`，并以 `status=enabled` 条件更新和 `RowsAffected` 完成 CAS，之后才增加用户额度。该顺序是本次兑换审核的基准。
- `Zer0Echo/uniapi` 的 `model/redemption.go` 已有 `RedeemResult` 区分余额与套餐兑换的先例，但它统一返回对象，没有覆盖 classic/旧脚本对裸数字的兼容。本项目的混合响应契约必须增加控制器级测试。
- GitHub 未检索到可直接复用的 `gift_reset_count`、`grantValuePackageResetCountTx` 或同名台账实现。赠卡逻辑应保持本项目内的最小收口，不新增泛化框架。
- 检索到的 `subscription_plans ADD COLUMN` 示例多为单数据库或 PostgreSQL 专用写法，不适合本项目。SQLite 补列继续沿用仓库既有列探测与 `ALTER TABLE ... ADD COLUMN` 模式，MySQL/PostgreSQL 由 GORM 迁移覆盖。

## 5. 关键语义决策

### D1 落地页品牌测试

状态：已接受。

结论：接受“zh 保持中文原样，其他语言要求非空译文”。依据：

- `42f8c7d` 是当前分支祖先，且当前 locale 已存在多语言译文；
- 当前产品定稿允许各语言译文，继续要求所有语言保持中文会与实际设计冲突；
- 非中文 locale 的历史内容仍有中英文混合，不能虚构“必须不同于中文原文”的约束；
- 测试继续精确锁定 zh 原文，其他语言使用 `trim().length > 0` 防止键缺失、空串或纯空白；
- 本次不修改开始页文案，只校正测试契约与名称。

### D2 `/api/user/topup` 响应契约

状态：已接受并完成 classic 兼容修复。

目标契约：

- `quota`：`data` 为数字；
- `subscription`：`data` 为 `RedeemResult` 对象；
- `reset_card`：`data` 为 `RedeemResult` 对象；
- 错误响应格式保持不变。

静态证据：classic 当前直接执行 `renderQuota(data)` 与 `quota + data`，对象响应会造成错误展示与本地额度损坏。需增加三类型控制器契约测试，并让 classic 只在 quota 数字响应时更新本地额度；对象响应仅显示对应成功结果。

### D3 每次套餐成交均赠卡

状态：已接受，幂等与订单快照回归断言已补齐。

结论：新开、续费、升级是独立成交，每次按成交时套餐配置赠送；同一订单的重复完成回调不得重复赠送。现有成功订单分支会在赠卡路径前返回，需用余额与台账数量明确锁定该行为。

## 7. 部署与回滚原则

1. 先在本地完成全部测试和生产构建，不在停服窗口内编译。
2. 先上传到版本化临时路径并验证文件，再切换当前版本。
3. 迁移随应用启动执行；新列均为增量列，回滚应用无需立即回滚数据库。
4. 切换后以进程、HTTP、静态资源和关键业务接口形成闭环测量。
5. 任一关键测量失败且 60 秒内不能修复，立即恢复旧二进制/镜像并重启。
6. 回滚前禁用或避免继续发放旧版本不能识别的 `reset_card` 兑换码。
